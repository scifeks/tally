# Classification gates

Domain agents apply these gates in order to every potential finding. Gates
classify findings by adjusting severity, confidence, and finding_type. They
do NOT eliminate findings. Report everything; classify accurately. Gate
results go into the finding's `reasoning` field and `meta.gate_results`.

## Gate 1: Reachability

### Question

Is this code reachable from a production entry point?

### Classification rules

| Reachability | Severity | Confidence | finding_type | Notes |
|---|---|---|---|---|
| Reachable from production entry point | No adjustment | No adjustment | `["vulnerability"]` | The finding is in live code |
| Reachable only through dev/test paths | Downgrade one tier | No adjustment | `["weakness"]` | Code exists but only runs in dev |
| Reachable but through indirect dispatch (callback, factory, event) | No adjustment | Downgrade to `probable` unless taint is traced | `["vulnerability"]` | Mark `meta.indirect_dispatch: true` |

### How to check

Cross-reference the finding's file:line against the recon manifest's call
graph and partition file lists. If the file appears in a partition, the code
is reachable. If not, it should be in the dead code inventory (handled by
the dead code sweep, not domain agents).

## Gate 2: Attacker control

### Question

Is the input that reaches this sink actually attacker-controlled?

### Classification rules

| Input source | Confidence adjustment | finding_type | Notes |
|---|---|---|---|
| Direct user input (HTTP params, CLI args, file upload, WebSocket message) | `confirmed` or `probable` | `["vulnerability"]` | Trace the variable from the entry point to the sink |
| Indirect via store (DB, cache, queue, session) | `probable` | `["vulnerability"]` | Note: data was written by a user at some earlier point |
| Config file or environment variable | `potential` | `["weakness"]` | Attacker typically cannot control config, but config injection exists |
| Server-generated or hardcoded | `potential` | `["weakness"]` | Note the path that could make it attacker-controlled in the future |
| Framework-internal (request ID, timestamp, session token generated by the framework) | `potential` | `["weakness"]` | Typically safe but the pattern itself is dangerous |

### How to check

Read the recon manifest's input inventory. Trace the variable reaching the
sink back to its origin. If the origin is a numbered input from the
inventory, the input is attacker-controlled.

## Gate 3: Sanitization

### Question

Is there effective sanitization between the source and the sink?

### Classification rules

| Sanitization status | Severity adjustment | Confidence | finding_type | Notes |
|---|---|---|---|---|
| No sanitization | No adjustment | No adjustment | `["vulnerability"]` | The finding is unmitigated |
| Sanitization present, context matches sink | Downgrade one tier | `potential` | `["weakness"]` | Note: defense exists but verify it covers all attack vectors |
| Sanitization present, context MISMATCH (e.g., HTML sanitizer on SQL sink) | No adjustment | `probable` | `["vulnerability"]` | Report the mismatch explicitly in reasoning |
| Type coercion or cast (e.g., `int()`, `intval()`) | Downgrade one tier | `potential` | `["weakness"]` | Safe for this input but pattern is fragile |
| Allowlist check | Downgrade two tiers | `potential` | `["weakness"]` | Verify the allowlist is complete |

### Context matching

Context match means the sanitizer transforms or encodes characters relevant
to the sink's parser. An HTML entity encoder is context-matched to HTML
output sinks but NOT to SQL, command, or URL sinks. A SQL parameter
placeholder is context-matched to SQL sinks but NOT to HTML output.

## Gate 4: Impact

### Question

Does exploiting this give the attacker a meaningful new capability?

### Classification rules

| Impact | Severity adjustment | Notes |
|---|---|---|
| Data exfiltration, RCE, auth bypass, privilege escalation | No adjustment | Full-impact vulnerability |
| Limited read (existence oracle, timing side-channel, error disclosure) | Downgrade one tier | The attacker learns something but cannot act on it directly |
| Write to attacker-controlled location only (XSS to self, SSRF to attacker's server) | Downgrade one tier | Limited blast radius |
| No observable difference between exploit and normal behavior | `informational` severity, `["weakness"]` | The pattern is dangerous but not currently exploitable |

## Recording gate results

Every finding must include gate results in two places.

### In the `reasoning` field

One sentence per gate summarizing the verdict. Example:

```
Gate 1: reachable via POST /api/users (SG-2). Gate 2: input `username`
from request.json is direct user input. Gate 3: no sanitization between
input and SQL execute call. Gate 4: attacker can exfiltrate all user
records.
```

### In the `meta.gate_results` field

JSON object with structured verdicts:

```json
{
  "reachability": "production",
  "attacker_control": "direct",
  "sanitization": "none",
  "impact": "data_exfiltration"
}
```

Valid values for each gate:

- `reachability`: `production`, `dev_only`, `indirect`
- `attacker_control`: `direct`, `indirect_store`, `config`,
  `server_generated`, `framework_internal`
- `sanitization`: `none`, `context_match`, `context_mismatch`,
  `type_coercion`, `allowlist`
- `impact`: `data_exfiltration`, `rce`, `auth_bypass`,
  `privilege_escalation`, `limited_read`, `limited_write`,
  `no_observable`

## Cumulative adjustments

Gates apply cumulatively. A finding that is:

- Reachable (no adjustment) + direct input (confirmed) + no sanitization
  (no adjustment) + full impact (no adjustment) = `severity: <default>`,
  `confidence: confirmed`, `finding_type: ["vulnerability"]`

A finding that is:

- Reachable only through dev path (severity -1, weakness) + indirect store
  input (probable) + context-matched sanitizer (severity -1, potential,
  weakness) + limited read (severity -1) = severity drops 3 tiers from
  default, `confidence: potential`, `finding_type: ["weakness"]`

Severity cannot go below `informational`. Confidence cannot go below
`potential` (do not set `false_positive`; that is for the adversarial
verification pass only).
